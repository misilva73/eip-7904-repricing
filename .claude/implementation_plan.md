# EIP-7904 Repricing — Implementation Plan

## Goal

A static multi-page site, deployed to GitHub Pages, summarising the EIP-7904
repricing analysis. The pipeline:

1. `benchmarkoor-fetch` pulls benchmark data from the Benchmarkoor API into
   `data/raw/`, driven by `fetch.yaml`.
2. `evm-gasfit` fits NNLS regressions on the runtimes (driven by `fit.yaml`)
   and emits the proposal artifacts into `data/gasfit/`. Glue adjustment is
   enabled, so all three reports are produced: `new_gas_proposal.md`,
   `runtime_estimation_autogenerated_report.md`, and
   `glue_opcodes_autogenerated_report.md`.
3. A build script renders Jinja2 templates into `site/`, pulling structured data
   (CSVs, fit summaries) from `data/gasfit/` and copying selected figures.
4. GitHub Pages serves `site/` from `main`.

Deployment is intentionally low-automation: a few iterative runs, then a final
commit-and-push.

## Decisions locked in

| Decision | Choice |
| --- | --- |
| Test scope | **Compute + stateful** — `fetch.yaml` pins both the jochennet compute and stateful suites. Compute drives the target-op fits; stateful/full runs feed the glue-opcode analysis. |
| Suite pinning | **Pin suite hashes in config** for reproducibility (two hashes, see `fetch.yaml`). |
| Glue adjustment | **Enabled** in `fit.yaml` — produces the glue reports/CSVs and the glue runtime page. |
| Site builder | **Jinja2 templates + vanilla JS**. `build_site.py` renders one HTML page per template, reading structured data from `data/gasfit/`. Dynamic filtering (runtime page) is client-side JS hide/show on a single rendered page — no JSON fetch, no SPA. |
| Page set | **5 pages**: landing, new-gas results, runtime model results, glue runtime results, methodology. Shared header/nav via a base template. |
| Data in repo | **Commit `data/` alongside `site/`** so the site is self-contained and auditable. |

## Configs

### `fetch.yaml` (benchmarkoor-fetch ≥ 0.2.0)

```yaml
query:
  fork: amsterdam
  run_id_pattern: '.*-full.*'
  start_date: 2026-05-27
  suites:
    - 3182dda7b93dee61 # jochennet compute
    - a11611f320a39015 # jochennet stateful
```

Network/test_type are not set because the run is identified by the two **pinned
suite hashes** instead (the `suites` subcommand —
`benchmarkoor-fetch suites --network <n> --fork <f> --test-type <t>` — resolves
the latest matching hash if you ever need to re-pin). `run_id_pattern` is a
regex (matched with `re.fullmatch`) — new in 0.2.0, replacing the old
`run_type`. `http`, `output`, and `cache` are left at defaults; notably
`output.trace_parquet` defaults to `true`, so `data/raw/` gets `trace.parquet`
in addition to `runtimes.csv`, `opcounts.json`, `bench_data.parquet`, and
`meta.json`.

Auth lives in the `BENCHMARKOOR_TOKEN` env var, never in this file (the config
loader rejects a token key). The token is loaded from a gitignored
`secrets.json` at the repo root (e.g. `{"BENCHMARKOOR_TOKEN": "bmk_..."}`); the
`Makefile` reads it with `jq` and exports it before invoking `benchmarkoor-fetch`
(or pass `--token` directly). The README documents that anyone reproducing the
analysis needs to request their own Benchmarkoor API key and create their local
`secrets.json`.

### `fit.yaml` (evm-gasfit ≥ 0.0.2)

```yaml
version: 1
anchor_rate: 100000000          # 1e8 — flag ops below 100 Mgas/s
clients:                         # required field; ethrex dropped by omission
  - besu
  - erigon
  - geth
  - nethermind
  - reth
gas_costs:
  fork: osaka                    # gas-cost table fork (distinct from the amsterdam benchmark fork)
output:
  plots: true
glue_adjustment:
  enabled: true
models:
  presets:
    # Opcodes touched by EIP-7904
    - arithmetic_div
    - arithmetic_sdiv
    - arithmetic_mod_bits
    - arithmetic_smod_bits
    - arithmetic_addmod_bits
    - arithmetic_mulmod_bits
    - keccak
    # Precompiles touched by EIP-7904
    - precompile_ecrecover
    - precompile_blake2f
    - precompile_blake2f_uncachable
    - precompile_bls_g1add
    - precompile_bls_g2add
    - precompile_bn128_add
    - precompile_bn128_add_uncachable
    - precompile_bn128_pairing
    - precompile_bn128_pairing_alt
    - precompile_point_evaluation
    - precompile_point_evaluation_uncachable
    - precompile_p256verify
    - precompile_p256verify_uncachable
```

evm-gasfit now ships 101 named presets, so the EIP-7904 ops are selected by name
under `models.presets` — no hand-written `ModelSpec`s. The presets carry their
own internals: `keccak` models base + per-word via `fixture_params`
(`bytes_to_words`), and the precompile presets set
`target_operation_count_source: STATICCALL` and a `filter_by` selector. The
`_bits` arithmetic presets model the variable (bit-width) param; the constant
ops (`arithmetic_div`, `arithmetic_sdiv`, `keccak` base, the precompiles) come in
the same list. This `_bits`-for-MOD/SMOD/ADDMOD/MULMOD, constant-for-DIV/SDIV
split is the intended per-op gas-param shape.

Two confirmed facts about the gas-cost baseline: (a) `osaka` is the intended cost
table even though the benchmarks ran on `amsterdam`, and evm-gasfit's bundled
GasCosts table knows `osaka`; (b) every preset's `target_coef` gas-param name is
expected to resolve in that osaka table — any genuinely new 7904 param that errors
because it isn't present must be declared under `new_params`.

## Orchestration

A top-level `Makefile` drives the pipeline. Steps 1–2 are direct CLI
invocations; step 3 is a real Python script.

<!-- markdownlint-disable MD010 -->
```makefile
BENCHMARKOOR_TOKEN := $(shell jq -r .BENCHMARKOOR_TOKEN secrets.json)
export BENCHMARKOOR_TOKEN

.PHONY: all fetch gasfit site clean

all:
	$(MAKE) fetch
	$(MAKE) gasfit
	$(MAKE) site

fetch:
	benchmarkoor-fetch run --config fetch.yaml --out data/raw/

gasfit:
	evm-gasfit run --config fit.yaml \
		--runtimes data/raw/runtimes.csv \
		--opcounts data/raw/opcounts.json \
		--out data/gasfit/

site:
	python scripts/build_site.py

clean:
	rm -rf data/ site/
```
<!-- markdownlint-enable MD010 -->

Usage:

```bash
# one-time: create secrets.json with {"BENCHMARKOOR_TOKEN": "bmk_..."}
make fetch     # → data/raw/   (reads token from secrets.json)
make gasfit    # → data/gasfit/
make site      # renders site_src/templates → site/, copies figs
# or just: make
```

`build_site.py` does the substantive work: load CSVs and parsed-markdown
summaries, set up the Jinja2 environment, render each template, copy the
relevant PNG subtrees (`proposal/`, `runtime/`, `glue/`) from
`data/gasfit/figs/` into `site/figs/`, and copy `site_src/assets/` into
`site/`.

Contributor toolchain adds `make` and `jq` on top of Python. The CLI flags above
match the real interfaces: `benchmarkoor-fetch run` takes `--config`/`--out`;
`evm-gasfit run` takes `--config`, separate `--runtimes` and `--opcounts` file
paths (there is no input-directory flag), and `--out`. Glue adjustment reads
opcode counts from `opcounts.json`, so no extra input is needed beyond the two
estimator-input files.

## Pages

All pages extend `base.html`, which provides the header, top nav (links to the
five pages), and reproducibility footer (pinned suite hash, run timestamp,
evm-gasfit / benchmarkoor-fetch versions, commit hash).

### 1. Landing — `index.html`

Static narrative. No data dependencies; survives a gasfit re-run untouched.

- EIP-7904 framing (links to eips.ethereum.org and magicians discussion).
- Key takeaway: one-paragraph summary of which ops need a bump and why.
- Cards linking to the four other pages.

### 2. New gas results — `new-gas.html`

Adapted from `data/gasfit/new_gas_proposal.md`. Sections:

- **Worst-case proposal table**: one row per gas param with proposed, current,
  diff (from `new_gas.csv` / the proposal report's diff table).
- **Per-client breakdown**: pivot of `new_gas_all_params.csv` — rows = gas
  params, columns = clients, cells = per-client proposed values. Highlights
  the worst-case cell per row.
- **Warnings & poor-fit selections** (if any) — surfaced from the proposal
  report.
- **Figures**: `figs/proposal/heatmap.png` (per-client/per-param log2-ratio
  heatmap) plus the per-param `figs/proposal/provenance__<gas_param>.png` files,
  copied from `data/gasfit/figs/proposal/`. (There is no `by_client.png`.)

`build_site.py` reads the CSVs directly (not the markdown) and renders the
tables via the Jinja template, so styling and column ordering stay under the
template's control.

### 3. Runtime model results — `runtime.html`

Adapted from `data/gasfit/runtime_estimation_autogenerated_report.md`. Each
`(test_name, target_opcode, client, model_by_combo)` section becomes a
`<section data-opcode="…" data-client="…">` block containing the NNLS summary
(preformatted) and the three regression / bootstrap / diagnostics PNGs.

Two `<select>` controls at the top (opcode, client) drive
`runtime_filter.js`, which toggles `display:none` on sections whose data
attributes don't match. "All" is an option on both filters.

Build-time: `build_site.py` reads `data/gasfit/results.csv` for the section
metadata and reuses the existing PNGs in `data/gasfit/figs/runtime/`. Fit
summaries — the preformatted text block in the markdown — are extracted from
`runtime_estimation_autogenerated_report.md` by parsing fenced code blocks
under each `##` heading. (Alternative considered: regenerate summaries from a
parquet of fit objects. Rejected — adds a serialization dependency on
evm-gasfit internals.)

### 4. Glue-opcode runtime results — `glue.html`

Same shape as the runtime page but driven by
`data/gasfit/glue_opcodes_autogenerated_report.md` and
`data/gasfit/glue_opcodes_by_test.csv`. Filters: client, glue_opcode. Figures
from `data/gasfit/figs/glue/`.

Per section, surface the headline stats from the report: `nobs`,
`glue_runtime_ms`, `p_value`, `rsquared`, plus the NNLS summary block.

### 5. Methodology — `methodology.html`

Static narrative. Documents the full pipeline:

- Benchmarkoor suites, pinned hashes, network/fork.
- NNLS regression model: target coefficient, `model_by` axes, bootstrap
  iterations, glue adjustment status.
- Anchor (100 Mgas/s) and how the worst-case-across-clients selection works.
- Filters, now all expressed in config rather than a pre-gasfit script: the
  ethrex client is dropped by omission from `clients`; per-op fixture exclusions
  (e.g. `bn128_add_infinities`, the `test_arithmetic` selection for
  MOD/SMOD/ADDMOD/MULMOD) ride along inside each preset's built-in `filter_by`.
- Reproducibility: how to re-run end-to-end.

## Deployment

GitHub Pages → `main` branch, `/site` folder. No CI. You commit `site/` (and
`data/`) and push when the analysis is final.
